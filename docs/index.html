Current build

Frontend concept, not a live exchange

No secret or payment is stored by this local build

The seller form clears submitted keys and fails closed because the secure vault, usage proxy, database and settlement contracts are not connected

The 3D interface, provider catalog, seller flow, buyer flow and explicit wallet connection work locally. Live routing requires a dedicated backend and contracts

Sellers

List capacity

  1. Choose a provider

    Select the provider and workload you are authorized to route

  2. Set limits

    Define a price, daily spend ceiling, model allowlist and request limits

  3. Submit securely

    Send the key directly to a server-side encrypted vault over TLS. Never persist it in browser storage

  4. Receive usage revenue

    Verified usage receipts determine the seller balance available for BNB settlement

Sellers

Key security

  • Encrypt secrets with a managed KMS or HSM and use envelope encryption
  • Never write raw keys to logs, analytics, client bundles, localStorage or onchain data
  • Use provider-specific spending caps, model allowlists, request limits and automatic revocation
  • Proxy every buyer request so buyers receive a marketplace route token, never the provider credential
  • Rotate or revoke a route after suspicious usage, provider rejection or seller withdrawal

Sellers

Revenue

A production marketplace should calculate gross usage, provider cost, protocol fee and seller revenue separately. Sellers need a live ledger for each request and a clear dispute window before settlement

Buyers

Buy AI usage

  1. Select a workload

    Text, image, video, voice, embeddings or another supported capability

  2. Set a maximum budget

    The route must stop before the approved limit is exceeded

  3. Receive a temporary route token

    The buyer calls INPUT, not the seller's provider key

  4. Pay for measured usage

    Settlement uses signed receipts generated by the metering layer

Settlement

BNB settlement

A buyer can fund a bounded session or prepaid balance. The backend signs usage receipts, the contract releases only the verified amount, and unused funds return to the buyer. No contract is connected in this local build

Protocol

Required architecture

  1. Marketplace API

    Authentication, listings, budgets, route tokens and seller controls

  2. Encrypted key vault

    KMS-backed storage with isolated decrypt permission

  3. Provider adapters

    One adapter per provider for request validation, usage extraction and error handling

  4. Metering and receipts

    Immutable usage records signed before settlement

  5. BNB contracts

    Escrow, protocol fees, seller balances, withdrawals and dispute controls

Protocol

Provider rules

Public API access does not automatically grant the right to resell, sublicense or transfer usage. Every provider and seller account must be reviewed before activation. Providers that prohibit the intended model remain disabled unless written authorization is obtained
